## 1. 概要

自然言語の指示を受け取り、シミュレーション内の Franka Emika Panda が
指定された物体を指定されたトレイへ運ぶシステムを実装した。

指示文を `「赤いブロックを紫のトレイに入れて」` から
`「赤い缶を黄色のトレイに入れて」` に書き換えるだけで、
掴む物も置き先も変わる。**コードは 1 行も変えていない。**

本システムの立ち位置を一言でいうと、

> **シミュレータ内部の物体座標を、制御に一切使っていない。**

把持位置はカメラの RGB 画像と深度バッファだけから推定している。
`mjData` の真値を参照するのは、実行後に精度を採点するときだけである。

AI の利用は**学習済みモデルの推論のみ**（追加学習なし）。
オープン語彙物体検出 OWLv2 を使い、指示文中の語をそのまま検出クエリにしている。

## 2. 課題設定と、そこに至った考え

「ロボットが何かのタスクを実行する」だけなら、物体の座標を決め打ちして
IK を解けば動画は撮れる。しかしそれは、シミュレータの外に出た瞬間に成り立たない。

実世界で同じことをするには、最低でも次の 2 つが要る。

1. **言葉と物体を結びつける**（どれが「赤いブロック」なのか）
2. **画像から 3 次元の把持位置を出す**（座標は誰も教えてくれない）

そこで本課題では、この 2 つを埋めることを目標に据えた。
タスク自体（pick & place）は平凡でよく、**情報の流れを実世界と同じ向きに
揃えること**を設計目標とした。

## 3. システム構成

```
指示文 "赤いブロックを紫のトレイに入れて"
   │
   ├─ ① 指示解析    instruction.py   対象スロット / 置き先スロットに分解
   │                                 → "a red cube" / "a purple box"
   ├─ ② 接地        perception.py    OWLv2 が語を画素（bbox）に結びつける
   │
   ├─ ③ 3D 化       camera.py        bbox 内を深度で逆投影 → 点群
   │                grasp.py         天面の点群から物体軸と天面高さを推定
   │
   ├─ ④ 動作        ik.py            減衰最小二乗 IK（位置 + 姿勢の 6 次元）
   │                controller.py    approach → descend → grasp → lift
   │                                 → transfer → place → release
   └─ ⑤ 自己検証    perception.py    実行後の画像を再び OWLv2 に通し、
                                     対象の中心が置き先の内側にあるかで成否判定
```

シーンには **赤いブロック / 赤い缶 / 緑のブロック / 青い缶** と、
紫・黄の 2 つのトレイを置いた。
赤い物体が 2 つあるのは意図的で、後述の対照実験のためである。

## 4. 技術的な中身

### 4.1 指示の解析（規則ベース）

指示文は規則ベースのスロット抽出で `(色, 名詞)` の組に分解する。
ここを LLM にしなかったのは、**難しいのは解析ではなく接地の側**だと考えたため。
語彙を増やしたいときは `instruction.py` の表に 1 行足すだけでよく、
検出器の再学習は要らない。これがオープン語彙検出を選んだ理由でもある。

### 4.2 オープン語彙物体検出による接地

OWLv2 (`google/owlv2-base-patch16-ensemble`) に
`"a red cube"` のようなクエリを渡し、バウンディングボックスを得る。
クラス定義を事前に持たないので、シーンに新しい物体を足しても
コード側の変更が要らない。

### 4.3 RGB-D からの把持位置推定 — 本課題で一番苦労した箇所

bbox から 3D 把持位置を出す手順は次の通り。

1. bbox 内の全画素を、深度とカメラ内部パラメータ
   （`f = (H/2) / tan(fovy/2)`）でワールド座標へ逆投影する
2. 作業台の高さより上の点だけを残す（机を捨てる）
3. bbox に紛れ込んだ隣の物体を、中央値から 6cm → 3.5cm の 2 段階で切る
4. 残った点の上位パーセンタイルを天面高さとする
5. **天面付近の点だけ**を使って物体の水平位置を決める
6. 天面から 15mm 下を掴みにいく

**手順 5 が効いた。** 最初は点群全体の中央値を物体軸としていたが、
単眼なのでカメラ側の面しか見えず、重心が手前へ系統的に **約 19mm** 偏った。
4cm の物体に対して 19mm は致命的である。

凸物体を斜め上から見ると **天面は全部見えている**ことに気づき、
天面の点だけを使うようにしたところ誤差は **約 7mm** に下がった。
さらに、天面も斜めから見ると手前側ほど点が密になるため、
中央値ではなく外れ値を切った上での「両端の中点」に変えて **約 3mm** となった。

| 物体軸の推定方法 | 水平方向の誤差 |
|---|---|
| 点群全体の中央値 | 約 19 mm |
| 天面の点の中央値 | 約 7 mm |
| 天面の点の両端中点（採用） | **約 3 mm** |

### 4.4 逆運動学と動作生成

Panda の 7 関節に対し、手先位置 + 姿勢の 6 次元誤差を減衰最小二乗法で解く。

```
dq = Jᵀ (J Jᵀ + λ²I)⁻¹ e      （λ = 0.08）
```

擬似逆行列ではなく DLS にしたのは、特異点近傍で解が発散するのを避けるため。
ヤコビアンは `mujoco.mj_jac` に TCP の座標を直接渡して得ている
（MJCF に TCP 用の site を足さずに済む）。

Panda のアクチュエータは位置サーボなので、IK の解をそのまま `ctrl` に入れる。
降下区間は関節空間ではなく**手先の直線**を細かく刻み、各点で IK を解いている。

### 4.5 自己検証

実行後にもう一度カメラを撮り、対象と置き先を OWLv2 で検出して、
**対象の中心が置き先の枠の内側にあるか**で成否を判定する。
ここでもシミュレータの状態は見ていない。実機でも同じ判定ができる。

## 5. 工夫した点（まとめ）

1. **シミュレータの真値を制御に使わない**という制約を自分に課し、
   知覚 → 3D 化 → 動作の流れを実世界と同じ向きに揃えた
2. **単眼の点群重心バイアスを発見し、天面の点だけを使って 19mm → 3mm に改善**した
3. **オープン語彙検出**を採用し、語彙追加に再学習が不要な構成にした
4. **自己検証**を入れ、成否判定まで画像で閉じるようにした
5. **対照実験**（VLM vs 色閾値）を設計し、VLM を使う必然性を数字で示した
6. **動画をコードから生成**し、指示文・検出枠・フェーズ・判定を焼き込んだ
   （編集作業を挟まないので、結果と動画が常に一致する）

## 7. うまくいかなかったこと・考察

### 7.1 OWLv2 は人間と同じ語を使わない

当初、置き先を `"an orange tray"` で検出しようとしたが **まったく検出されなかった**。
調べると、OWLv2 はこの形状を `"tray"` ではなく **`"box"`** と呼び、
さらにこの色を `"orange"` ではなく **`"yellow"`** と見ていた。

| クエリ | スコア |
|---|---|
| `an orange tray` | 検出なし |
| `an orange box` | 検出なし |
| `a yellow box` | **0.37** |
| `a purple tray` | 検出なし |
| `a purple box` | **0.43** |

対処として、**日本語の表示は「トレイ」のまま、英語クエリだけ `box` に写像**し、
トレイの色自体も黄色に変更した（`instruction.py` の対応表を 1 行変えるだけで済んだ）。

これは実装上は小さな修正だが、示唆は小さくない。
VLM を部品として使うときは、**こちらの語彙をモデルの語彙に合わせにいく**必要があり、
その対応表はドキュメントではなく**実測で決める**しかない。
「どのクエリが通るか」を測る仕組みを最初から用意しておくべきだった。

### 7.2 円柱が掴めない — 原因を取り違えて時間を使った

立方体は最初から掴めたが、**円柱だけが持ち上げ中に指から滑り出た**。
摩擦係数・`condim`・`solref`・`impratio`・`noslip_iterations` を振ってみたが、
どれも結果が変わらなかった。

接触点を出力して分かったのは、

- 指のパッドは円柱に**線接触**しかしていない（接触点が立方体の 1/3）
- 持ち上げ 10cm までは保持できており、そこから徐々に水平方向へ滑り出ていた

摩擦係数を 4.0 まで上げると「持ち上がる」ようになったが、
グリッパ幅を見ると **48mm の円柱を 44mm まで潰していた**。
接触が軟らかくなりすぎて指がめり込んでいただけで、物理的には成立していない。
数字だけ見て「直った」と判断しかけた点は反省している。

最終的な対処は、**見た目は円柱のまま、衝突形状だけを外接する箱に置き換える**
（衝突プロキシ）という、ロボティクスのシミュレーションで一般的な方法を採った。
箱の半幅は円柱の半径と同じなので指が触れる位置は見た目と一致し、
はみ出す角は 45 度方向＝グリッパから見えない向きにある。
**知覚はレンダリング結果しか見ていないので、この置き換えは検出側に影響しない。**

これにより 4 物体すべてで把持が安定した。
実機では円柱の把持はグリッパのパッド形状（V 溝やゴム）で解くのが普通であり、
その意味でも「シミュレータ上の形状の問題」として切り分けるのが妥当だと判断した。

### 7.3 持ち上げの目標を「指令値」にしていた不具合

持ち上げを `把持目標 + 上方向` としていたため、
サーボの残差（数 mm）の分だけ **横に押す動き**が混ざっていた。
立方体は面接触なので耐えてしまい、円柱でだけ症状が出るという厄介な不具合だった。
現在は **実際の TCP** から真上に持ち上げている。

### 7.4 残っている制約

- **把持姿勢が真上固定**。物体の主軸を点群から推定して手首角を合わせれば、
  細長い物体にも対応できるはずだが未実装
- **開ループ**。把持に失敗しても検知して掴み直す処理がない。
  自己検証はエピソード末尾の 1 回だけで、途中のフィードバックに使えていない
- **カメラが 1 台・固定**。物体が互いに隠れると破綻する。
  手先カメラを足すか、視点を変えて再観測するのが素直な拡張
- **指示解析が規則ベース**。「一番左のやつ」のような空間参照には答えられない

### 7.5 実機への展開

本システムで実機に持っていけない部分は、原理的には
「深度センサの質」と「把持の物理」の 2 点に絞られる。
知覚 → 3D 化 → IK の流れ自体は、カメラを RealSense に、
MuJoCo を ROS 2 のノードに置き換えればそのまま載る構造にしてある。
実際、`perception.py` / `grasp.py` は MuJoCo に依存していない
（`CameraView` という小さなデータ構造だけを受け取る）。
